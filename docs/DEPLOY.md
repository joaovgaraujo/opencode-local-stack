# DEPLOY: standing this up on Windows, Linux, or macOS

`install.py` is cross-platform (Windows, Linux, macOS/Apple Silicon), detects
your hardware, and picks a matching engine + release automatically. This doc
covers the Windows/Linux llama.cpp path in detail. For macOS/Apple Silicon
(rapid-mlx), see [`MACOS.md`](MACOS.md) instead, it's a different enough
engine (MLX weights, unified memory, no llama.cpp binary) to warrant its own
doc. For the common case, just run the installer.

## Fastest path: one command

```
python install.py
```

Opens the GUI wizard. With Homebrew Python on macOS, the installer adds the
matching `python-tk@X.Y` formula when `_tkinter` is missing. Windows' standard
python.org installer includes Tk; Linux may need `python3-tk`, and unsupported
or headless environments fall back to the text wizard with a specific repair
message. Either way it:

1. Detects OS, GPU vendor + VRAM, RAM, free disk.
2. Shows the model/quant catalog filtered and sorted by what plausibly fits
   (see [`MODELS.md`](MODELS.md) for how the fit estimate works).
3. Downloads (or reuses) a matching llama.cpp release and the GGUF.
4. Starts the server, waits for `/health`, runs `tests/validate.py`, sets up
   OpenCode, and runs an agentic smoke test.
5. Writes `RESULTS.md`.

For a scripted/unattended install (CI, a second machine, whatever), skip the
wizard entirely:
```
python install.py --model qwen3.6-35b-a3b --quant Qwen3.6-35B-A3B-UD-Q4_K_M.gguf \
    --profile primary --non-interactive
python install.py --list-models     # see every model id / quant filename
```

Useful flags: `--profile auto` (default: maximum context with VRAM reserve),
`--profile conservative` (force smaller context, more headroom), `--skip-tests`,
`--model-path <existing.gguf>`, `--bin-dir <existing llama.cpp folder>`,
`--backend auto|cuda|vulkan|rocm|cpu`, `--port <N>`, and `--stop-when-done`.
Repeat `--extra-server-arg` to append one llama-server argument and persist it
in `settings.json`; it replaces the matching installer default (for example
`-ctk`, `--fit`, `-ub` or `--reasoning`). An argument beginning with `-` must use the equals form
(`--extra-server-arg=--cont-batching`); provide its value separately
(`--extra-server-arg=--threads --extra-server-arg 16`). These llama.cpp-only
flags are rejected on the macOS Rapid-MLX path.

Node.js (required for OpenCode) is never installed silently. If it's missing,
`install.py` prints the right command for your OS and stops. Pass
`--install-node` to let it run `winget install OpenJS.NodeJS.LTS` for you on
Windows. On Linux there's no single package manager to assume, so it always
just prints the command (`apt`/`dnf`/`pacman`/nvm) rather than guessing which
one you use and needing `sudo` on your behalf.

## What's in the repo

```
install.py                    # ONE-SHOT installer + validator (Windows, Linux, macOS)
installer/                    # hardware detection, model catalog, download, server lifecycle, GUI/CLI wizards
installer/rapidmlx_setup.py   # macOS/Apple Silicon engine (see docs/MACOS.md)
opencode.json                 # OpenCode -> local endpoint config (regenerated by install.py per selection)
models/                       # <- drop a GGUF here, or let the installer download it (llama.cpp engine only)
tests/validate.py             # the 4 functional tests (env-driven: LLAMA_BASE_URL / LLAMA_MODEL)
tests/vram_logger.ps1         # Windows VRAM/RAM sampler
docs/MODELS.md                # the model catalog, quant list, fit-estimate methodology
docs/MACOS.md                 # macOS/Apple Silicon (rapid-mlx) - read this first if you're on a Mac
docs/RESULTS.md               # historical validated results (Qwen3.6, primary profile)
docs/DEPLOY.md                # this file
```

Generated on first run (git-ignored, not in the repo):
```
llama.cpp/          prebuilt llama.cpp release matching your OS + GPU backend (llama.cpp engine only)
models/*.gguf        the model weights (llama.cpp engine only - rapid-mlx downloads its own)
settings.json        model, context and thinking for opencode-local
run.ps1 / run.sh     start only the server (macOS gets run.sh only)
RESULTS.md           per-machine pass/fail summary
```

## Starting it after install

`opencode-local` (installed on PATH, see the README) starts the server from
`settings.json` and opens OpenCode in the current folder. To start only the
server, for another client:
```powershell
opencode-local --server-only          # or .\run.ps1 / ./run.sh, which call the same thing
opencode-local --stop
```

The exact arguments it passes to llama-server are in `.server-state.json`
after a start. Point OpenCode at the server by hand:
```
npm install -g opencode-ai@1.19.6 @ai-sdk/openai-compatible@3.0.94
# then merge ./opencode.json into %USERPROFILE%\.config\opencode\opencode.json
# (Linux: ~/.config/opencode/opencode.json); opencode-local does this for you
opencode      # then /models -> pick the local one
```

## GPU backend selection (what `install.py` picks and why)

This table is the llama.cpp engine only. macOS never reaches it -
`hwdetect.pick_engine()` routes any Apple Silicon Mac to the rapid-mlx engine
before backend selection is even considered (see [`MACOS.md`](MACOS.md)); an
Intel Mac falls through to this table's logic but there's no Darwin entry
wired up in `download.py` yet, so it stops with a clear error rather than
guessing.

| OS | GPU | Backend chosen | Notes |
|---|---|---|---|
| Windows | NVIDIA | `cuda` | official prebuilt Windows CUDA release + cudart |
| Windows | AMD | `rocm` (HIP) | prebuilt `win-hip-radeon-x64` release |
| Windows | other/unknown | `vulkan` | prebuilt `win-vulkan-x64` release |
| Windows | none detected | `cpu` | prebuilt `win-cpu-x64` release |
| Linux | NVIDIA | `cuda` | prebuilt `ubuntu-cuda-12.8/13.5` release + CUDA runtime, matched to the driver; needs glibc 2.38+, else built from source (see below) |
| Linux | AMD | `rocm` | prebuilt `ubuntu-rocm-7.2-x64` release |
| Linux | other/unknown | `vulkan` | prebuilt `ubuntu-vulkan-x64` release |
| Linux | none detected | `cpu` | prebuilt `ubuntu-x64` release |

### Linux + NVIDIA: prebuilt CUDA or a source build

llama.cpp publishes Linux CUDA builds (x64 and arm64) for CUDA 12.8 and 13.5.
The installer picks the newest one the driver supports (`nvidia-smi` reports
it: a 13.4 driver gets the 12.8 build) and puts the CUDA runtime libraries
next to `llama-server`. After unpacking it runs `llama-server --version` and
`--list-devices`, so a build that can't run or can't see the GPU is caught
before the model download.

Those builds need glibc 2.38 or newer (Ubuntu 24.04, Debian 13, Fedora 39 or
later). On an older system the prebuilt fails with `GLIBC_2.38 not found`, and
the installer compiles llama.cpp with CUDA from source instead when git,
cmake, a C++ compiler and the CUDA toolkit (`nvcc`, also looked up in
`/usr/local/cuda*/bin`) are installed. Ask for that build directly with:
```bash
./setup.sh --build-llamacpp                  # or: python3 install.py --build-llamacpp
```
It clones the matching llama.cpp release into `llama.cpp-src/`, builds only
`llama-server` for this machine's GPU (`CMAKE_CUDA_ARCHITECTURES=native`) and
copies it to `llama.cpp/`. Expect 5 to 20 minutes. Without the tools it stops
with the apt command to install them.

`--backend vulkan` uses the Vulkan prebuilt instead, and
`--bin-dir <folder>` any llama-server you built yourself.

## Expert placement (MoE models)

The server runs with `--fit on --fit-target 1536`: at start-up llama.cpp
measures the GPU, keeps the dense layers, KV cache and buffers on it, and
fills the remaining VRAM with expert layers, leaving 1,536 MiB free. The rest
of the experts stay in system RAM. On a simulated 12 GB card at 64K context
this gave 73 tok/s against 51 with every expert in RAM (`--cpu-moe`); see the
README for the table.

`--fit` measures VRAM when the server starts, so a game or another model
holding VRAM at that moment means fewer expert layers on the GPU (slower, but
it still loads). To change the margin, edit `fit_margin_mib` in
`settings.json`. In testing `--fit` used about 0.5 GB more than it planned, so
keep at least 1,024.

To place experts yourself, pass your own flags; they replace `--fit`:
```
python install.py ... --extra-server-arg=--n-gpu-layers --extra-server-arg 999 --extra-server-arg=--n-cpu-moe --extra-server-arg 28
```
On Windows with NVIDIA, NVIDIA Control Panel -> Manage 3D settings -> CUDA -
Sysmem Fallback Policy = Prefer No Sysmem Fallback makes an over-full card fail
with an error instead of running slowly from shared memory.

## Notes

- `--no-mmap` forces experts fully resident in RAM (skips the page cache) if
  prompt ingestion feels I/O-stalled; usually unnecessary with mmap and
  enough free RAM.
- One server instance per repository-managed install. `install.py` records the
  exact PID and resolved executable path in `.llama-server.pid`, and only stops
  that verified process on a later run. It does not use global `pkill` or
  image-name `taskkill`, so llama-server instances from other projects are
  left alone.
- Frontend is **OpenCode only**. Open WebUI was intentionally not set up.
- Gemma 4's jinja chat template has known thinking/tool-call interplay quirks
  on some llama.cpp builds. If you see garbled tool calls or `reasoning_content`
  leaking into `content`, update llama.cpp first (see the link in
  [`MODELS.md`](MODELS.md)).
